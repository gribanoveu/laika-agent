# 7. Находки в Alfa Atlas

Замечания к **исходному** приложению, накопившиеся при чтении его кода для переноса
(этапы F-1.1…F-1.13 из [06-port-plan.md](06-port-plan.md)). Документ адресован тому, кто
правит Atlas, а не тому, кто делает перенос.

Каждая находка помечена уровнем доказательности:

- **подтверждено** — прочитан код, приводящий к описанному поведению;

Ничего из перечисленного не воспроизводилось запуском: Atlas в этой сессии не собирался и
не запускался.

## B-1. `spans_from_backward_gap_symbols` падает на вложенных символах

**Файл:** `domain/chunk_index.rs:133` · **Уровень:** подтверждено · **Важность:** высокая

```rust
let mut prev_end: u32 = 0;
for (i, sym) in anchors.iter().enumerate() {
    let end = if i == last { content_len as u32 } else { sym.end_byte };
    spans.push(ChunkSpan { start_byte: prev_end, end_byte: end, .. });
    prev_end = sym.end_byte;
}
```

`prev_end` растёт монотонно, но функция **не сортирует якоря и не проверяет, что они не
пересекаются**. Якорь, чей `end_byte` меньше предыдущего — вложенный символ либо просто
неупорядоченный вывод индексера — даёт `ChunkSpan` с `start_byte > end_byte`. Потребитель
режет `content[start..end]` и паникует.

Сейчас это не воспроизводится только потому, что `JavaIndexer` сознательно не спускается в
тела методов, то есть **инвариант держится дисциплиной вызывающего, а не кодом**. Любой
новый `LanguageIndexer` — особенно порождённый обобщённым извлечением через `tags.scm`,
которое [05-gaps.md](05-gaps.md) §5.5 предлагает как следующий шаг, — воспроизводит панику.
Это же место уже один раз роняло воркер синхронизации (см. «шрам» в
[04-reuse-map.md](04-reuse-map.md) §4.6).

**Починка:** отсортировать якоря по `start_byte` на входе и либо пропускать вложенные
(`sym.end_byte <= prev_end`), либо схлопывать спан в пустой. Утверждение
`debug_assert!(start <= end)` не спасает релизную сборку и потому недостаточно.

## B-2. `default_allowed_tools` игнорирует свой параметр и разрешает всё

**Файл:** `domain/ai_access.rs:286` · **Уровень:** подтверждено · **Важность:** средняя
(вводящий в заблуждение контракт, не дыра)

```rust
pub fn default_allowed_tools(_mode: AiAccessMode) -> HashSet<ToolName> {
```

Параметр не используется, а тело перечисляет **все** варианты `ToolName` до единого.
При этом вокруг функции выстроен аппарат fail-closed: `ai_allowed_tools: Option<Vec<ToolName>>`
с правилом «настроенный пользователем список не расширяется молча», отдельные
`set_tool_allowed`/`allowed_tools`, миграции списка между версиями
(`PLAN_TOOLS_MIGRATION`, `SKILL_TOOL_MIGRATION`, `DEPENDENCY_SOURCES_MIGRATION`).

Собственный комментарий функции признаёт причину: «There's no frontend UI to customize this
allowlist today, so requiring opt-in here would ship the confirmation feature with no way to
ever turn it on». То есть механизм существует, охраняет множество, где разрешено всё, и его
единственный рабочий эффект — миграции, которые добавляют в список то, что и так там есть.

Настоящий контроль — `requires_confirmation`, и это в комментарии тоже сказано.

**Починка — выбрать одно из двух**, потому что текущее состояние обманывает читателя кода:
либо довести до конца (UI для списка, и тогда `mode` начнёт что-то значить), либо удалить
allowlist вместе с миграциями и оставить гейт подтверждений единственным механизмом. Второе
дешевле и честнее; при переносе выбрано оно.

## B-3. Снимки вызовов инструментов переотправляются на каждом чанке

**Файл:** `infra/llm_providers/openai_compatible.rs:667` · **Уровень:** подтверждено ·
**Важность:** средняя

```rust
if !tool_calls.is_empty() {
    tool_calls_acc.ingest(tool_calls);
    for (id, name, arguments) in tool_calls_acc.snapshots() {
        on_tool_call_delta(&id, name, arguments);
    }
}
```

`snapshots()` отдаёт **все** накопленные вызовы, а не только изменившиеся этим чанком.
Раунд с `N` вызовами и `M` чанками аргументов порождает порядка `N×M` событий вместо `M`, и
`N−1` из каждой пачки несут неизменившиеся данные. Для `writeFile` с большим содержимым,
рядом с которым модель начала второй вызов, это десятки лишних IPC-сообщений в секунду,
каждое с полной копией накопленных аргументов.

Функционально безвредно — фронт делает upsert по `id`. Но это лишний трафик ровно в тот
момент, когда поток и так самый плотный.

**Починка:** отдавать снимки только тех записей, чьи `index` пришли в этом чанке.
`ingest` уже знает этот список.

## B-4. `PendingApproval` сериализуется, но не десериализуется

**Файл:** `domain/llm.rs:553` · **Уровень:** подтверждено · **Важность:** низкая
(устойчивость)

```rust
#[derive(Debug, Clone, Serialize)]
pub struct PendingApproval { .. }
```

Контрольная точка возобновления — шесть полей, каждое из которых закрывает конкретную дыру
(`history`, `round`, `budget_used`, `event_seq`, `calls`, `todos`) — уходит на фронт
целиком, а возвращается в `llm_chat_stream_resume` **разобранной на отдельные параметры**.
Следствия:

- целостность контрольной точки держится на том, что фронт вручную соберёт обратно все
  шесть полей; забытое поле — это молча обнулённый потолок раундов или перенумерованный
  поток событий, а не ошибка компиляции;
- тип нельзя проверить round-trip-тестом, потому что обратного преобразования у него нет;
- незавершённый turn нельзя просто записать на диск и прочитать (это же называет
  [05-gaps.md](05-gaps.md) §5.6 среди недостающего).

**Починка:** добавить `Deserialize` и принимать контрольную точку одним аргументом. Тест на
round-trip тогда становится возможным и ловит потерю поля в момент правки, а не в проде.

## B-5. Мёртвая ветка в проверке пути

**Файл:** `domain/paths.rs:146` (`join_relative`) · **Уровень:** подтверждено ·
**Важность:** низкая, но место чувствительное

```rust
if part == ".." { return Err(ProjectError::PathEscape(..)); }
if Path::new(part).components().next() != Some(Component::Normal(OsStr::new(part))) {
    return Err(ProjectError::PathEscape(..));
}
```

Первая проверка недостижима: для `".."` компонент — `Component::ParentDir`, и вторая
отвергает его раньше. Обнаружено мутационным тестом при переносе — удаление первой проверки
не меняет ни одного исхода.

Само по себе безвредно, но это код, охраняющий границу доступа, и читатель обязан понимать,
какая строка живая. Через год кто-нибудь «упростит» вторую проверку, считая первую
работающей защитой от `..`.

**Починка:** удалить первую ветку, а объяснение про `..` перенести в комментарий ко второй.

## B-6. `.gitignore` учитывается только внутри git-репозитория

**Файл:** `infra/workspace_scanner.rs` · **Уровень:** условно · **Важность:** низкая

`WalkBuilder` не получает `require_git(false)`, а по умолчанию `ignore` honours `.gitignore`
**только если каталог является git-репозиторием**. Для Atlas это, скорее всего, не проявляется:
продукт открывает git-репозитории по определению.

Проявится, если существует путь, которым можно открыть не-репозиторий (или подкаталог вне
рабочего дерева): `grep` и обход индекса начнут видеть `node_modules`, `target`, `build`.

**Проверить:** может ли проект открыться на каталоге без `.git`. Если да — добавить
`require_git(false)`: лежащий в каталоге `.gitignore` это утверждение о том, что считать
мусором, независимо от того, запускали ли `git init`.

## B-7. Отказ по лимиту (HTTP 429) не обрабатывается нигде

**Файлы:** `services/llm_chat.rs:773-812`, `infra/llm_providers/openai_compatible.rs`
(`ok_or_status_error`) · **Уровень:** подтверждено · **Важность:** средняя, для
пользовательских провайдеров — высокая

`grep` по всему Rust-дереву не находит ни `429`, ни `Retry-After`, ни `retry_after`.
Единственный повтор в цикле turn'а — это:

```rust
Err(error)
    if retry_attempt < MAX_PEER_DISCONNECTED_RETRIES
        && !attempt_emitted_data.get()
        && is_peer_disconnected_error(&error.to_string()) =>
```

то есть повторяется **только** оборванное соединение. Любой не-2xx, включая 429, приезжает
из `ok_or_status_error` как `LlmError::Http("http status 429: …")` и обрывает turn целиком
(`Err(error) => return Err(error.to_string())`).

Заметно это тем, что рядом лежит `domain/llm_rate_limit.rs` (885 строк) — подробная
клиентская модель окна: три счётчика, скользящие 20 минут, рабочие часы, часовой пояс.
Она **предсказывает** лимит, чтобы до него не доводить, но живёт только для провайдера с
запечённым правилом в манифесте (`policy_for(preset)`; для всех прочих — `NoopPolicy`).

Отсюда и разрыв: приложение позволяет добавить **произвольного** OpenAI-совместимого
провайдера (`LlmProviderConfig` без пресета). Для него клиентской модели нет по построению,
а 429 — не экзотика, а штатный ответ любого публичного API на длинном агентном turn'е.
Пользователь, направивший Atlas на такой эндпойнт, получает не паузу, а падение turn'а
посреди работы — с уже выполненными инструментами и без возможности продолжить.

**Починка** — небольшая и вся в одном месте: отдельный вариант ошибки для 429 с разобранным
`Retry-After`, и ветка в том же `loop`, что уже повторяет обрыв. Два правила из
существующего кода переносятся как есть и являются главными:

1. повтор допустим, только если попытка **ничего не отдала** (`attempt_emitted_data`) —
   иначе текст допишется второй раз, а уже запущенный инструмент выполнится повторно;
2. ожидание режется на секундные срезы с проверкой отмены, иначе кнопка «стоп» не работает
   всё время паузы.

Ожидание дольше пары минут разумно превращать в честную ошибку с указанием срока: turn,
молча спящий пять минут, неотличим от зависшего приложения.

В переносе это F-1.13 (`domain/llm_retry.rs`), при том что сама модель окна не переносилась.

## Проверено и **не** является ошибкой

Перечислено, чтобы никто не тратил время повторно — по каждому пункту у меня была гипотеза,
и код её опроверг.

| Гипотеза | Что в коде на самом деле |
|---|---|
| `deleteDirectory` с `recursive: true` на `"."` сносит корень документации | `docs_fs::delete_project_dir:356` — `if canonical == root { return Err(InvalidName) }`. Защита есть |
| Legacy-формат в `secret_store` оставляет старые блобы взаимозаменяемыми | `read_secret_file` переписывает такой блоб в v1 при первом же чтении — legacy-путь вытесняется, а не живёт вечно. Fall-through с v1 на legacy узкий и намеренный (нонс, случайно начавшийся с `ATLS`, 1 к 2³²), гарантию purpose не ломает |
| Политика «без `unwrap()` вне тестов» нарушается | В прочитанных модулях единственный `expect` — `last_mut().expect("just pushed")` сразу после `push`. Политика соблюдается |
| Обрезка диффа может упасть на многобайтовом символе | `truncate_on_line_boundary` считает символы и режет по границе строк. Корректно |
| Лимит `grep` считает строки, а не совпадения | Считает совпадения; контекстные строки принадлежат попаданию и лимит не съедают |
| `save_api_key` при недоступном мастер-ключе затирает все остальные ключи | `load_all` действительно вырождается в пустую карту, но запечатывание требует того же ключа, что и открытие: `save_all` падает раньше, чем что-либо будет записано. Строгая загрузка на запись сделала бы хуже — при повреждённом блобе нельзя было бы сохранить ни одного нового ключа |

## Не ошибки, а осознанные пробелы

Уже перечислены в [05-gaps.md](05-gaps.md), повторяются здесь только как напоминание о
приоритете:

1. **Нет защиты от записи в файл, изменившийся после чтения агентом** (§5.6, CA-3.10). Это
   единственный пункт списка, приводящий к **потере данных пользователя**: агент прочитал
   файл, человек поправил его в редакторе, агент записал свою устаревшую копию поверх.
   Обходится тем же механизмом, что «сначала прочитай файл»: реестр «путь → хэш на момент
   чтения» отвечает на оба вопроса одним поиском. В переносе это F-1.6a.
2. **Отказ в подтверждении не несёт причины** (`ToolCallDecision`). Модель, которой сказали
   только «отклонено», характерно повторяет тот же вызов, затем его близкий вариант.
   Необязательное поле `reason` заканчивает это за один раунд.

## Чужой урок, уже усвоенный апстримом

Не дефект: в коде апстрима это уже починено, а запись здесь — чтобы починку не отменили
по невнимательности при переносе.

**`infra/chat_store.rs:88-99`.** Комментарий над `run_migrations` описывает случившееся:
база, записанная более новой сборкой, раньше **отвергалась** — и это стоило пользователю
всей истории разом. Каждая команда `chat_*` открывает хранилище, поэтому один номер
`user_version` превратил и список, и загрузку, и сохранение в ошибки, которые фронтенд
глотает; в окне чат-лист просто оказывался пустым. Сейчас такая база читается как есть, а её
`user_version` не трогается, чтобы миграции более новой сборки увидели то, что записали сами.

Два вывода, оба применены в F-3.8:

1. Более новый формат — не повреждение. Различать их надо **до** разбора, потому что ответ
   разный: повреждённое показать, более новое не трогать.
2. Единое хранилище делает любую такую ошибку тотальной. Здесь — файл на чат: нечитаемый
   чат стоит одной строки в списке, а не всей истории.

## Чего в этом документе нет

Не читались и потому не оценивались: агентный цикл `services/llm_chat.rs` — прочитан один
блок повторов из 2826 строк, и это по-прежнему самая вероятная область нетривиальных
дефектов, индексный слой (`repo_index`,
`embedding_sync`, `index_store`, языковые индексеры), весь фронтенд, `commands/` целиком,
git-слой глубже сигнатур `git_ops`. Отдельно стоит заметить, что §5.9 самих доков описывает
уже **исправленный** дефект языкового фильтра как самый дорогой по последствиям — то есть
область индекса уже показала, что умеет прятать ошибки такого класса.
