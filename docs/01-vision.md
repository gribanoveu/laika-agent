# 1. Видение и границы

## 1.1 Что строим

Кодинг-агент, который работает в репозитории пользователя: читает код, ищет по нему,
правит файлы, запускает команды, объясняет что сделал. Два равноправных фронта над
одним ядром:

- **CLI** — основной режим. Интерактивная сессия в терминале и headless-вызов
  (`agent -p "..."` с машиночитаемым выводом) для скриптов и CI.
- **Десктоп-приложение** — оболочка в духе Claude Code Desktop: то же ядро, но с
  нормальным просмотром диффов, карточками подтверждений, деревом сессий, историей.

Это не два продукта и не «CLI, обёрнутый в Electron». Это одно ядро и два адаптера над
общим протоколом событий turn'а ([03-architecture.md](03-architecture.md)).

## 1.2 Для кого

Разработчик, который уже живёт в терминале и в git. Не «AI-ассистент для всех», а
инструмент, которому доверяют писать в рабочее дерево — со всеми вытекающими
требованиями к подтверждениям, откату и наблюдаемости.

## 1.3 Основные сценарии

| # | Сценарий | Что должно работать |
|---|----------|---------------------|
| S-1 | «Почини падающий тест» | поиск по репо → чтение → правка → запуск теста → повтор до зелёного |
| S-2 | «Объясни, как работает X» | поиск, чтение, ответ без единой записи на диск |
| S-3 | «Сделай рефакторинг по всему проекту» | план → множественные правки → подтверждения пачкой → дифф целиком |
| S-4 | «Разбери этот стектрейс» | чтение логов из stdin/файла, навигация по символам |
| S-5 | Headless в CI | без TTY, без подтверждений (явный allowlist), стабильный exit code и JSON-вывод |
| S-6 | Долгая сессия | компакция истории, возврат к сессии через сутки, ветвление от сообщения |

## 1.4 Границы скоупа (осознанно НЕ делаем в v1)

- Не делаем свой редактор/IDE. Дифф показываем, но правит пользователь в своём редакторе.
- Не делаем облачный бэкенд, аккаунты, шаринг сессий. Всё локально.
- Не делаем мультиагентность (сабагенты, параллельные ветки исполнения) — закладываем
  место в протоколе, но не реализуем.
- Не делаем свой язык плагинов. Точки расширения — MCP и skills-файлы.
- Не делаем удалённое исполнение/контейнеры. Песочница — средствами ОС, локально.

## 1.5 Чем отличаемся от того, что берём за образец

Два места, где у Alfa Atlas уже сделано лучше, чем в типовом самодельном агенте, и это
стоит сохранить как отличие продукта:

- **Бюджет цикла считается по весу инструментов**, а не по числу итераций. Дешёвая
  последовательность чтений живёт долго, дорогие поиски обрываются рано.
- **Дедупликация повторных результатов внутри turn'а.** Повторное чтение того же файла
  с тем же хэшем не пересылает содержимое второй раз. На длинных turn'ах это разница
  между «влезли в контекст» и «не влезли».

И одно, где Atlas слабее любого кодинг-агента и что придётся строить с нуля: **исполнение
команд** ([05-gaps.md](05-gaps.md)).

## 1.6 Принципы

1. **Безопасно по умолчанию.** Запись и исполнение — под подтверждением, пока
   пользователь явно не расширил allowlist. Явно настроенный пользователем allowlist не
   расширяется молча при добавлении нового инструмента в следующей версии.
2. **Ядро не зависит от UI-фреймворка.** Ни `tauri::`, ни `clap` внутрь ядра не попадают.
3. **Ошибки — типизированные данные вглубь стека**, строка только на границе процесса/IPC.
4. **Всё, что агент сделал, видно и отменяемо.** Лог вызовов инструментов, дифф на каждую
   запись, git как механизм отката.
5. **Контекст — это бюджет.** Каждое решение в цикле оценивается по тому, сколько токенов
   оно стоит на десятом раунде, а не на первом.
